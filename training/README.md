# GDKVM re-release training

This workstream produces **new re-release checkpoints** from the rewritten code/data stack.

It is not a historical-checkpoint reproduction path.

## Reference training contract

- single GPU;
- eager execution;
- contiguous memory layout;
- FP32 reference mode;
- canonical contiguous-NPY dataset caches;
- local JSONL observability is always available;
- W&B is optional and not required for training;
- accepted checkpoints are SHA256-identified;
- final scientific tables are generated by the evaluation protocol, not by ad-hoc Trainer console output.

## 3090-like resource envelope

The default configs may cap the PyTorch CUDA allocator to about **23 GiB** when running on a larger GPU such as RTX 5090.

This tests whether the training path fits an RTX 3090-class memory budget. It does **not** turn a 5090 timing into a measured 3090 timing.

### Batch-size qualification

A one-step CAMUS memory screen on RTX 5090 under the 23 GiB allocator cap qualified batch sizes 2, 4, 8, and **10**. Batch 10 peaked at about **20.54 GiB reserved VRAM**, so the reference CAMUS config keeps batch size 10 instead of artificially reducing it to 1.

This preserves the old training-scale intent more closely while remaining inside the 3090-like memory envelope. The screen is engineering evidence only, not a convergence or throughput claim.

## Commands

CAMUS:

```bash
python scripts/train_gdkvm.py \
  --config training/configs/camus-v1.yaml \
  --train-cache /path/to/camus-train-cache \
  --val-cache /path/to/camus-val-cache \
  --test-cache /path/to/camus-test-cache \
  --output /path/to/run
```

EchoNet-Dynamic uses `training/configs/echonet-v1.yaml`.

For a short engineering qualification, add `--max-iterations 2`. This does not produce a scientific checkpoint.

Formal runs fail closed on partial/wrong-split caches. The v1 configs bind the expected full sample counts, so an engineering subset cannot accidentally be used as a release-training dataset.

## Checkpoint authority

A re-release checkpoint becomes eligible for publication only when its run receipt records:

- code SHA;
- full training config SHA256;
- data-cache manifest SHA256 values;
- runtime profile;
- seed;
- checkpoint byte size + SHA256;
- training completion status.

The release workstream then binds accepted evaluation receipts to that checkpoint.


## Evaluate a newly trained checkpoint

After a checkpoint is produced, bind it to the current metric protocol with:

```bash
python scripts/evaluate_gdkvm_checkpoint.py \
  --config training/configs/camus-v1.yaml \
  --checkpoint /path/to/checkpoint.pth \
  --cache /path/to/camus-test-cache \
  --split test \
  --output /path/to/checkpoint-eval.json
```

A formal evaluation refuses partial/wrong-split caches. For an engineering-only path test, `--max-samples N` is allowed and the receipt is labeled `engineering-smoke`.

This command currently owns segmentation metrics and patient-level confidence intervals. It deliberately does **not** claim LVEF/clinical agreement until the upstream clinical reconstruction method is separately bound and qualified.
